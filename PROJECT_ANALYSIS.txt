1. WHAT THIS PROJECT IS
--------------------------------------------------------------------------------
This is a prototype "Plant IT Support Portal" — an internal dashboard for a
manufacturing plant's IT department. The core idea:

  - Plant floor workers report IT problems (broken scanners, hung HMI PCs,
    dead printers, network drops, etc.) over WhatsApp group chats.
  - The backend simulates/receives those WhatsApp messages, runs them through
    a simple keyword-based "AI" classifier, and automatically opens, updates,
    resolves, or reopens a support ticket ("Complaint") based on the message.
  - A React dashboard shows IT staff a live, auto-refreshing view of all open/
    in-progress/resolved complaints, broken down by plant area, equipment,
    and category, plus a "WhatsApp Simulator" page to demo the pipeline
    without needing a real WhatsApp Business account.

It is a two-tier app:
  - backend/  → Java 17 + Spring Boot 3.2 REST API, PostgreSQL via JPA/Hibernate.
  - frontend/ → React 18 + TypeScript + Vite + TailwindCSS SPA.
  - docker-compose.yml ties both together with a Postgres container.

This looks like a demo/prototype build — it has mock authentication, an
in-memory-style "AI" classifier (keyword matching, not a real ML model), and
a WhatsApp integration that is optional/feature-flagged (disabled by default,
only a "simulate" endpoint is wired to the UI).

3.6 integration/ai/ — pluggable complaint classifier
  - ComplaintClassificationProvider (interface)
      classifyMessage(String message) → ClassificationResult
  - ClassificationResult (model)
      isComplaint, category, equipment, machine, intent, priority,
      confidence
  - MockClassificationProvider (the only implementation registered)
      A deterministic, keyword/substring-matching "AI":
        • Lowercases the message.
        • If it contains "scanner" → category=Scanner, equipment=Scanner,
          priority=HIGH.
        • "hmi" → HMI / HMI PC / HIGH.
        • "zebra"/"printer" → Zebra Printer / Printer / HIGH.
        • "internet"/"network"/"lan"/"wifi" → Network / Network / HIGH.
        • "pc"/"computer"/"windows" → Computer / PC / MEDIUM.
        • Phrases like "check kar raha", "dekh raha" → intent=IN_PROGRESS,
          priority=HIGH, confidence=0.86.
        • Resolution phrases ("working hai", "fixed", "resolved", "theek ho
          gaya", etc.) → intent=RESOLUTION_DETECTED, priority=MEDIUM,
          confidence=0.93.
        • Reopen phrases ("abhi bhi", "still", "phir", "not working") →
          intent=REOPENED, priority=HIGH, confidence=0.91.
        • Urgency words ("urgent", "line stopped", "main hmi", "stop") →
          priority escalated to CRITICAL, confidence=0.94.
        • isComplaint is true only when intent stayed at the default
          "NEW_COMPLAINT" — i.e. any recognized status-update phrase
          (in-progress/resolved/reopened) is treated as an update to an
          EXISTING complaint, not a new one.
      This is clearly a stand-in for a real NLU/LLM-based classifier — it's
      simple rule matching tuned to the exact demo scenarios used in the
      WhatsApp Simulator page and seed data (mixed Urdu/English "Roman Urdu"
      phrases).

3.7 integration/whatsapp/ — pluggable WhatsApp transport
  - WhatsAppMessageProvider (interface): start(), stop(), isConnected(),
    getMonitoredGroups(), sendMessage(destination, message)
  - MockWhatsAppProvider: no-op implementation (always "connected", does
    nothing on send) — this is what's active by default since
    app.whatsapp.enabled=false.
  - WhatsAppCloudProvider: real implementation, only registered when
    app.whatsapp.enabled=true. Builds a WebClient pointed at
    https://graph.facebook.com/v20.0, posts messages to
    /{phoneNumberId}/messages with a Bearer token, using a hand-built JSON
    payload (messaging_product=whatsapp, recipient_type=individual, type=
    text). Fire-and-forget via `.subscribe()` (no back-pressure/result
    tracking beyond logging).

3.10 service/ + service/impl/ — business logic
  - CategoryService / CategoryServiceImpl
      listAll() → maps Category entities to CategoryDto.
  - DashboardService / DashboardServiceImpl
      getSummary(): loads ALL complaints, computes:
        • total = size (used as "whatsappComplaints" KPI)
        • open = count where status == OPEN
        • inProgress = count where status == IN_PROGRESS
        • resolvedToday = count where resolvedAt's date == today
        • critical = count where priority == CRITICAL and status != RESOLVED
        • averageResolutionTime is hardcoded to the string "Live" (not
          actually computed from data)
        • complaints = top 20 most recent, mapped to ComplaintSummaryDto
          (joining in category/equipment/location/reporter/group names).
  - EmployeeService / EmployeeServiceImpl
      listAll(), create() (sets createdAt/updatedAt to now), update(id)
      (findById().orElseThrow() then overwrites all fields — full replace,
      not partial patch, despite being exposed via @PatchMapping).
  - WhatsAppGroupService / WhatsAppGroupServiceImpl
      listAll() — maps WhatsAppGroup entities to DTOs. (Unused — no
      controller wired, see 3.3.)
  - WhatsAppService / WhatsAppServiceImpl — THE CORE PIPELINE:
      Two public entry points:
        a) simulateIncomingMessage(WhatsAppSimulateRequest request)
           — used by the frontend's WhatsApp Simulator page via
             POST /api/whatsapp/simulate.
           — Looks up the WhatsAppGroup by name (case-insensitive) and the
             Employee by name; if the group isn't found, silently returns.
           — Runs the message through ComplaintClassificationProvider.
           — Persists a WhatsAppMessage row (externalMessageId is a
             "mock-<timestamp>" placeholder).
           — Delegates to applyClassificationToComplaint(...) with a
             complaint-number prefix of "IT-".
           — Also calls whatsappProvider.sendMessage(employeeName, message)
             — with the Mock provider this is a no-op; it's presumably meant
             to simulate an ack/reply.
        b) processRealIncomingMessage(senderPhone, messageText,
           externalMessageId, phoneNumberId)
           — used by WhatsAppWebhookController when real WhatsApp Cloud API
             messages arrive.
           — Finds the Employee by matching whatsappNumber exactly OR by
             comparing the last 10 digits (crude phone-normalization to
             handle country-code differences).
           — Picks the group as "the first WhatsAppGroup with
             monitoringEnabled = true" — i.e. it does NOT actually route by
             which WhatsApp number/group the message came from; it just
             grabs whichever monitored group happens to be first in the
             DB. This is clearly a placeholder ("in production, link groups
             to phone numbers" per the code comment) rather than real
             multi-group routing.
           — Same classify → save WhatsAppMessage → applyClassificationToComplaint
             flow, with prefix "WA-".
           — Wrapped in try/catch that just logs errors (never rethrows) so
             a bad webhook payload won't crash the request.

      applyClassificationToComplaint(...) — the actual state machine:
        - If classification.isComplaint() is FALSE (i.e. the AI decided this
          message is a status update, not a new issue):
            • Searches all complaints for one from the SAME WhatsApp group,
              NOT already RESOLVED/CLOSED, whose aiCategory matches the new
              classification's category, picking the most recently created
              match.
            • If none found, logs a warning and does nothing (the update is
              dropped).
            • If found: maps intent → status:
                IN_PROGRESS         → status = IN_PROGRESS
                RESOLUTION_DETECTED → status = RESOLVED, resolvedAt = now
                REOPENED            → status = REOPENED, resolvedAt = null
              Then updates updatedAt and saves.
        - If classification.isComplaint() is TRUE (new issue):
            • Resolves a Category by matching classification.category
              (case-insensitive), falling back to the "Other" category if no
              match.
            • Resolves Equipment by matching its `type` field to
              classification.equipment (case-insensitive); null if none
              found.
            • Generates a complaint number as `<prefix><currentMillis % 1e6>`
              — NOT guaranteed unique (a modulo of the clock, not a real
              sequence/UUID — collisions are possible, especially under
              simulated rapid-fire testing).
            • Builds and saves a new Complaint: title = first line/80 chars
              of the message (extractTitle helper), description = full raw
              message text, status = OPEN, source = "WhatsApp".
      Note: `location` is never set on newly created complaints (the field
      exists on Complaint but applyClassificationToComplaint never populates
      it) — so all auto-created complaints show `location: null`, even
      though Equipment/Employee have location/area data that could have been
      used to backfill it. This matches what's visible on the seeded demo
      complaints (which do have locations, because those are inserted
      directly in DataSeedConfig) versus complaints created through the
      simulator (which will have no location).

4.1 Bootstrapping
  - index.html: minimal shell, dark background classes, mounts <div id="root">,
    loads /src/main.tsx as an ES module.
  - main.tsx: creates a single `QueryClient`, then renders the app inside
    (outer→inner) StrictMode → QueryClientProvider → BrowserRouter →
    AuthProvider → App. Global CSS imported here.
  - App.tsx: top-level route table —
      "/login"  → LoginPage
      "/*"      → AppShell if isAuthenticated, else redirect to /login
    This means ALL other routing (dashboard, simulator) is nested inside
    AppShell, gated by a single top-level auth check.

4.2 hooks/useAuth.tsx — client-only mock auth
  - Hardcoded `demoUsers` map with 3 accounts:
      admin@plant.local / Admin@123 / role ADMIN
      supervisor@plant.local / Supervisor@123 / role SUPERVISOR
      viewer@plant.local / Viewer@123 / role VIEWER
  - On login(), checks email+password against this map (case-insensitive
    email); on success, writes the user object to `localStorage` under key
    "plantit-user" and updates React state.
  - On first render, initializes state by reading directly from
    localStorage (so a refresh keeps you logged in).
  - logout() clears localStorage and state.
  - isAuthenticated = !!user.
  - IMPORTANT: This is entirely client-side — passwords are hardcoded in the
    bundled JS, anyone can read them from devtools, and there is no
    server-side session/token of any kind (matches the backend having no
    AuthController and SecurityConfig permitting everything). This is
    strictly a UI-gating mechanism for demo purposes, not real security.

4.3 lib/api.ts — HTTP layer
  - Creates an axios instance with baseURL "/api" (proxied to
    http://localhost:8080 by vite.config.ts's dev server proxy) and JSON
    content-type header.
  - fetchDashboardSummary() → GET /dashboard/summary → returns response.data.
  - simulateWhatsApp(payload: {groupName, employeeName, message}) →
    POST /whatsapp/simulate.
  - default export is the raw axios instance (not otherwise reused
    elsewhere in the current code beyond these two helpers).

4.4 components/layout/

      "/"          → LiveDashboardPage
      "/simulator" → WhatsAppSimulatorPage
      "*"          → redirect to "/"
    This is the actual authenticated app's page router (nested under the
    "/*" route from App.tsx).
  - Sidebar.tsx: static nav with two links (Dashboard, WhatsApp Simulator),

  - Topbar.tsx: search input (local state only, not wired to any filtering

4.5 pages/
  - LoginPage.tsx (default export)
      Controlled form with email/password state (pre-filled with the admin
      demo creds), a show/hide password toggle, a "Remember me" checkbox
      (visual only, not implemented), a "Forgot password?" button (no
      handler), a demo-credentials panel listing all 3 accounts, a
      "Fill Admin Demo" button that resets the form fields, and calls
      login()/navigate('/') from useAuth on submit; shows an error message

      NOTE: There's a stray `<button>Click Me!</button>` at the end of the
      form with no onClick handler and no visible purpose — looks like
      leftover/debug markup that should probably be removed.

  - DashboardPage.tsx (named export `DashboardPage`)
      A fully-featured KPI/analytics dashboard BUT it is built almost
      entirely from hardcoded mock arrays defined at module scope (`incoming`,
      `zones`, `categories`, `equipment`, `trendData`) — only the top 6 KPI
      tiles pull from the real `fetchDashboardSummary()` query; everything
      else (the complaint feed list, per-zone breakdown, category pie chart,
      equipment table, open/resolved area chart) is static demo data that
      does not reflect the actual database.
      NOTE: This component is imported in App.tsx but is NEVER actually
      rendered by any <Route> — AppShell's internal routes use
      LiveDashboardPage instead. So DashboardPage.tsx is dead/unreachable
      code left over from an earlier iteration of the dashboard.

  - LiveDashboardPage.tsx (named export `LiveDashboardPage`) — THE REAL
    DASHBOARD actually mounted at "/":
      • Uses useQuery with `refetchInterval: 5000` and
        `refetchOnWindowFocus: true` against fetchDashboardSummary() — this
        is the "live" polling behavior (auto-refresh every 5 seconds).
      • KPI tiles: WhatsApp Complaints, Open, In Progress, Resolved Today,
        Critical Issues, Avg. Resolution — all from live `data`.
      • Derives (via useMemo, all client-side from `data.complaints`):

          - zones: grouped by the first segment of `location` split on
            " / " (so location strings are expected in a "Area / detail"
            format — but as noted in 3.10, complaints created via the
            simulator never get a location set, so they'll all bucket under
            "Unassigned").
          - equipment: grouped by `equipment` field into

--------------------------------------------------------------------------------
5. END-TO-END DATA FLOW (how a WhatsApp message becomes a dashboard card)
--------------------------------------------------------------------------------
  1. A message arrives either via:
       a) The WhatsApp Simulator UI → POST /api/whatsapp/simulate, or
       b) A real WhatsApp Cloud API webhook → POST /api/whatsapp/webhook
          (only active if app.whatsapp.enabled=true).
  2. WhatsAppController / WhatsAppWebhookController hand the raw text off to
     WhatsAppServiceImpl.
  3. WhatsAppServiceImpl resolves the sending Employee and target
     WhatsAppGroup, then calls MockClassificationProvider.classifyMessage()
     to get a category/equipment/intent/priority/confidence guess purely
     from keyword matching in the message text.
  4. A WhatsAppMessage row is always persisted (the raw inbound log).
  5. applyClassificationToComplaint() then either:
       - creates a brand-new Complaint (status OPEN) if this looks like a
         fresh issue, or
       - finds the most recent open/non-resolved Complaint in the same
         group+category and mutates its status (IN_PROGRESS / RESOLVED /
         REOPENED) based on the detected intent.
  6. The React frontend's LiveDashboardPage polls GET /api/dashboard/summary
     every 5 seconds, which re-aggregates ALL complaints from the DB (counts
     by status/priority, plus the latest 20 for the feed list) and returns a
     DashboardSummaryDto.
  7. The dashboard re-derives its charts/zone breakdowns/equipment table
     client-side from that same complaint list on every poll.

6. NOTABLE GAPS, INCONSISTENCIES & PROTOTYPE-ISMS
--------------------------------------------------------------------------------
These are things a reader should know before treating this as production
code:

  • No real authentication anywhere. Login is a hardcoded, client-side-only
    check (frontend/src/hooks/useAuth.tsx) with plaintext demo passwords
    shipped in the JS bundle. The backend's SecurityConfig permits all
    requests, and there's no AuthController/JWT issuing despite an unused
    `LoginRequest` DTO and unused `app.auth.token-secret` config existing.

  • "AI" classification is 100% rule-based keyword matching
    (MockClassificationProvider), tuned specifically to the exact demo
    phrases used in the seed data and the Simulator's 7 canned scenarios —
    not a real ML/LLM classifier, despite the "aiConfidence"/"aiCategory"
    naming implying otherwise.

  • WhatsApp group routing for REAL incoming messages
    (processRealIncomingMessage) doesn't actually route by which number/
    group the message came from — it just grabs "the first
    monitoring-enabled group" in the whole table. A code comment
    acknowledges this ("in production, link groups to phone numbers").

  • Generated complaint numbers (`prefix + System.currentTimeMillis() %
    1_000_000`) are not guaranteed unique — a collision is possible,
    especially when firing several simulated messages quickly, and the
    `complaintNumber` column has a unique DB constraint, so a collision
    would throw a runtime exception.

  • New complaints created through the pipeline never get a `location` set
    (only the hand-seeded demo complaints have one), causing them to show as
    "Unassigned" in the live dashboard's zone breakdown.

  • Dead/unreachable code:
      - frontend/src/pages/DashboardPage.tsx is imported in App.tsx but
        never routed to (AppShell's internal routes use LiveDashboardPage
        instead) — effectively unreachable.
      - backend WhatsAppGroupService/Impl has no controller consuming it.
      - dto/whatsapp/WhatsAppWebhookVerification is unused (the controller
        binds verification params individually via @RequestParam instead).
      - ComplaintEvent and ComplaintMessage entities/repositories exist in
        the schema but nothing in the current service layer ever writes to
        them — no audit trail or message-linking is actually populated yet.
      - mapstruct is a declared Maven dependency but no @Mapper interfaces
        exist in the codebase.
      - react-hook-form and zod are frontend dependencies but aren't used by
        any current component (forms are plain controlled inputs).
      - A stray, handler-less `<button>Click Me!</button>` sits at the
        bottom of the login form in LoginPage.tsx.
      - tailwind.config.js defines custom `industrial`/`status` color
        tokens that the actual components don't use (they use Tailwind's
        stock slate/sky/rose/amber/emerald classes instead).

  • WhatsAppSimulatorPage's employee/group dropdowns are hardcoded lists
    that don't match the full seed data exactly (e.g., the "Quality IT
    Complaints" group and the 5th/6th seeded employees are absent from the
    simulator's dropdown options), and aren't fetched from the backend's
    /api/employees or the (unused) group-listing service — so adding a new
    employee via POST /api/employees won't make them selectable in the
    simulator without editing this hardcoded array.

  • EmployeeController's PATCH endpoint does a full field overwrite (not a
    true partial patch) — every field must be resent even though HTTP PATCH
    semantics usually imply partial updates.

  • Most repository lookups in WhatsAppServiceImpl use `.findAll()` +
    in-memory Java stream filtering (e.g., finding an employee by WhatsApp
    number, or a group by name) rather than the more efficient derived
    query methods already defined on the repositories (e.g.
    `EmployeeRepository.findByWhatsappNumber` exists but
    `processRealIncomingMessage` re-implements the matching logic manually
    with a stream + substring comparison instead of calling it).

  • docker-compose.yml runs the frontend service via `npm run dev` (Vite's
    dev server) rather than a production build served by e.g. nginx — fine
    for local demos, not suitable as-is for a real deployment.

7. HOW TO RUN IT LOCALLY (as configured)
--------------------------------------------------------------------------------
  Option A — Docker Compose (recommended for a quick full-stack demo):
    1. `docker compose up --build` from the repo root.
    2. Postgres comes up on 5432, backend on 8080, frontend (Vite dev
       server) on 5173.
    3. Visit http://localhost:5173, log in with one of the 3 demo accounts
       shown on the login page.

  Option B — Manual/local dev:
    1. Start a local Postgres (or reuse docker-compose's `postgres` service
       alone), matching the DB name/user/password in backend/.env.example.
    2. `cd backend && mvn spring-boot:run` (or run the packaged jar under
       target/) — reads env vars for DB connection; defaults to
       plantit/plantit/plant_it_support on localhost:5432 if unset.
    3. `cd frontend && npm install && npm run dev` — Vite dev server on
       5173, proxying `/api` calls to localhost:8080.
    4. On first backend start with an empty DB, DataSeedConfig automatically
       populates demo locations/categories/employees/groups/equipment/
       complaints.

  WhatsApp real integration (optional, off by default):
    Set WHATSAPP_ENABLED=true plus WHATSAPP_PHONE_NUMBER_ID,
    WHATSAPP_ACCESS_TOKEN, WHATSAPP_BUSINESS_ACCOUNT_ID, and
    WHATSAPP_WEBHOOK_VERIFY_TOKEN as env vars to activate
    WhatsAppCloudProvider and WhatsAppWebhookController, then point a real
    Meta WhatsApp Business webhook at
    https://<host>/api/whatsapp/webhook.
